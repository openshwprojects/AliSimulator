# The UART bootloader flash procedure on every image

Each image boots in the emulator and goes through tools/maciej_uart.py's flash procedure, the one verified on a physical Opticum STB HD N2: 'c' sent every 50 ms from power-on to hold the bootloader, the 'comtest 2' handshake, a CRC-checked full 'dump' as the backup, 'address' + 'transfer' + 'burn' of a main code chunk carrying a small test application (the demo's banner and a 'p' -> pong reply), a second full 'dump' compared byte for byte, 'reboot', the application's banner and pong, and a cold boot of a fresh machine from the flash the bootloader wrote.  Only UART bytes go in, at 115200 baud through a 16-byte receive FIFO.

Generated 2026-11-12 by `tools/bootloader_flash_survey.py` on the C++ emulator core; 686 images.

## Summary

Of the 686 images, 672 have a bootloader the emulator boots, and 461 of those (69 %) take the established procedure end to end: capture, handshake, a CRC-checked backup, the burn of a new main code chunk, a byte-for-byte readback, the loader's reboot into the new application and a cold boot from the written flash. 6 more go through it with their own main code burned again, renamed (its format -- encrypted or unknown -- cannot carry the test application).

173 more (26 %) take the same procedure in ALi's packet protocol, the only one their loaders speak (tools/ali_packet.py, written from the SDK's own loader sources): 640 of 672 (95 %) in all.

The rest: another request word 6; not captured by the paced 'c' 22; stopped part-way 4. The sections below explain each group.

## How the emulator runs the procedure

- UART: the host's bytes enter the 16-byte receive FIFO at 115200 baud line rate. Protocol bytes wait for room (as with flow control: the emulated CPU is slower than the real chip, so a loader can fall behind); the paced capture 'c' are lost when they meet a full FIFO, as on the wire. The C++ core logs the loader's transmitted bytes itself (a transmit-register rule), so a dump costs what the loader's own code costs: emulated seconds are instructions / 50 M.
- One pair of UART dumps per bootloader: the 686 images hold 222 distinct bootloaders (the bootloader chunk's bytes and the flash size). The backup and readback dumps run on one image of each and on every flash dump read from a box (195 images in all); the other images of a group still go through capture, handshake, transfer, burn, reboot and cold boot, and their written flash is compared with the expected image directly.
- The test application (firmware/maciej_app/hello.c: a banner, and 'p' answered with 'pong survey') is built for each image's main-code load address and UART and packed in the image's own main-code format: LZMA-alone, as the SDK's un7zip reads it (628 working images), or LZO1X behind a 16-byte header of sizes and Adler-32 sums (6; the M3801 loaders built by vic.wang). It replaces the main code chunk, CRC and all; the rest of the flash must stay as it was. Its start-up code (survey_start.S) copies it to the address it was linked for when a loader starts the main code elsewhere: with the chunk's load address left 0xFFFFFFFF most loaders use 0x80000200, but some use their own default (the Amiko / Amstar M3602 builds unpack and start it at 0x80008000).
- CRC checks: the C3505 chip model (and the C3503, built on it) normally rewrites the main code chunk's CRC to 'NCRC' (no CRC) so its loaders skip that check; the survey turns that off, so those loaders check the CRC of the chunk the survey writes ('CRC Check Result : Pass') as on the box. Every written chunk's CRC is also recomputed by the survey itself.
- Watchdog reboots: the loaders of 439 working images (M3503 204, C3505 147, M3801 43, C3503 25, M3821 20) answer 'reboot' by arming the watchdog for an immediate reset (0xB8018500 = 0xFFFFF000, then 0x67) and spinning. The emulator has no watchdog reset, so the survey starts a fresh machine from the flash the loader wrote -- what the chip's reset does.
- Flash above 0xB0000000: newer M3503 / C3505 loaders read an 8 or 16 MB flash linearly from 0xAFC00000 on, past 0xB0000000, where the SDK's older loaders switch windows; the emulator now maps the flash's tail there too (488 working images with more than 4 MB of flash).

## The packet protocol

- 173 images (M3602 126, M3801 47) have loaders built with the SDK's TRANSFER_FORMAT3_ONLY: they capture and echo 'comtest 2' like the others, then answer the two handshake bytes with 0xFF minus each byte (0xA7 0xA7 for 'XX'). They speak only ALi's packet (format 3) upgrade protocol, the one ALi's PC upgrade tools use, and tools/maciej_uart.py does not.
- tools/ali_packet.py speaks it, written from the SDK's own loader sources (refs/BootLoader/SRC/lib/libapplet/libbootupg3: Packet.c, lib_ash.c, lib_ashcmd.c). Every command, data block and status travels in a packet -- 'HEAD', type, index, length, a header CRC, the data and its CRC (CRC-32/MPEG-2, big-endian numbers); the dump comes as 1024-byte packets the host asks for one by one, and burn reports every sector it writes. After the same capture, '@' as the first handshake byte selects it (on these loaders any byte does). The commands are the classic ones: address, transfer, burn, dump, reboot.
- With it the survey runs the same procedure on them: 173 work end to end (AMIKO ALI3606, AMIKO HD8100 SERIES, AMIKO HD8140, AMIKO HD8140 T2C, AMIKO HD8200 SERIES, AMIKO HD8240, AMIKO HD8300 SERIES, AMIKO HD8840 and 23 more).

## What a pass means

A 'works' row means the image's own bootloader code, run instruction by instruction, accepted the established client's bytes, wrote exactly the flash the client expected (nothing outside the main code chunk changed), and booted the application it was given. The same procedure ran on a real Opticum STB HD N2 (dump_maciej.bin) with the results it has here (docs/maciej_bootloader.md). On another real box the timing differs -- its CPU runs several times faster than the emulator's 50 M instructions per second, so its loader drains the FIFO sooner and reaches its capture check earlier -- and parts the emulator does not model (a flash chip's protection bits, the board's UART wiring, a loader that also looks at a front-panel key) can still stop it. Read a 'works' row as: this bootloader implements the classic protocol and its flash-writing path the way the client expects.
